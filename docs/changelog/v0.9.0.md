# Pincer 0.9.0 — docTR OCR + Background Task Execution Rework

**Status:** Upcoming release

---

## TL;DR

Two independent additions on top of 0.8.0:

- **`doctr-mcp`** — a new bundled MCP server exposing OCR (optical character
  recognition) via [mindee/doctr](https://github.com/mindee/doctr).
- **Background task execution rework** — the hand-rolled cron fire-loop is
  replaced by durable [repid](https://pypi.org/project/repid/) actors, with
  chat-driven schedule management and a standalone worker for horizontal
  scaling.

---

## docTR MCP Server — OCR (6 tools)

**New module:** `src/doctr-mcp/` — a [FastMCP](https://github.com/jlowin/fastmcp)
server wrapping [mindee/doctr](https://github.com/mindee/doctr) for text
detection, recognition, full OCR, and key-information extraction (KIE) over
images and PDFs.

| Tool | Description |
|------|-------------|
| `ocr_document_text` | Quick plain-text read of an image or PDF — no geometry, the cheap default for "just read this" |
| `ocr_document` | Full end-to-end OCR: page → block → line → word tree with geometry, confidence, orientation, and language |
| `detect_text` | Text detection only — boxes/polygons, no recognition |
| `recognize_text` | Text recognition only, on a batch of pre-cropped word/line images |
| `extract_key_info` | Key-information extraction (KIE) — predictions grouped by detected class |
| `list_architectures` | Discover valid `det_arch`/`reco_arch` values |

Layout detection and table-structure extraction are not available in the
pinned `python-doctr==1.0.1` release — those exist only on doctr's
unreleased GitHub `main` branch.

**Architecture:**

- Lazy, bounded-LRU predictor cache (`DOCTR_MAX_CACHED_PREDICTORS`, default
  4) — detection/recognition model pairs are loaded on first use and evicted
  under memory pressure rather than all loaded eagerly at startup
- CPU by default (`DOCTR_DEVICE=cpu`); `cuda` supported but never
  auto-detected
- Defaults to **HTTP transport**, not stdio — the heaviest bundled server
  (torch-based), so it's the one workspace server where a persistent process
  paying model-load cost once matters most. See [MCP Servers](../core-components/mcp-servers.md#http-streamable-http-transport)
  for the stdio/HTTP tradeoff in general.
- Docker/compose setup with a pre-baked model cache volume
  (`doctr-model-cache`), wired into the root `docker-compose.yml` and CI
- Mocked test suite (no real model downloads in CI)

**Image/PDF handoff fix:** uploaded images are now saved to disk (as PDFs
already were) and passed to OCR tools via an explicit `file_path` argument,
instead of relying on the model to invent one or fabricate `image_b64` from
vision alone. For HTTP-transport servers running in isolated containers with
no shared filesystem, the MCP bridge transparently inlines `file_path`
arguments pointing into Pincer's own upload cache as base64 before the call
— scoped strictly to that cache directory.

**Config:**

```toml
[[mcp.servers]]
name      = "doctr"
transport = "stdio"
command   = "python"
args      = ["src/doctr-mcp/doctr_mcp/server.py", "--transport", "stdio"]
env       = { DOCTR_DEVICE = "cpu", DOCTR_CACHE_DIR = "${PINCER_DATA_DIR}/doctr_cache" }

# Or, for the HTTP/Docker deployment:
[[mcp.servers]]
name      = "doctr"
transport = "streamable-http"
url       = "http://doctr-mcp:8000/mcp"
timeout   = 120   # CPU inference is slow — longer timeout than other bundled servers
```

See [MCP Servers — environment variable reference](../core-components/mcp-servers.md#environment-variable-reference)
for the full `DOCTR_*` variable list.

## Background task execution rework — repid + chat-driven scheduling

The hand-rolled `CronScheduler` poll/fire loop (a bare `asyncio.create_task`
per due job, no redelivery on failure, no cross-process scaling) is replaced
by [repid](https://pypi.org/project/repid/) actors — durable, ack'd,
retryable execution, in-memory by default or Redis-backed for horizontal
scaling.

**New `src/pincer/tasks/` package:**

- `app.py` — registers the active broker (`InMemoryServer` or `RedisServer`,
  selected by `task_broker`) and owns the actor router
- `dispatch.py` — `ScheduleDispatcher`, a SQLite poll loop supplying the
  scheduling repid doesn't provide natively; polls `CronScheduler`'s store
  every `task_poll_interval` seconds and enqueues due schedules
- `actors.py` — `run_scheduled_action` and `process_webhook`, each wrapped
  in a bounded `tenacity` retry, then `on_error="nack"` for redelivery if
  retries are exhausted
- `context.py` — process-global deliverer/proactive/triggers for actor
  bodies (actors are plain functions with no access to a running process's
  locals)
- `delivery.py` — `Deliverer` protocol + `ResultEmitter`/`ResultRelay` pub-sub
  bridge, so actors never call a `ChannelRouter` directly. This is what
  makes the standalone worker below possible.

**Chat-driven scheduling** (`tools/builtin/schedule_tool.py`): `schedule_create`,
`schedule_list`, `schedule_remove`, `schedule_toggle` tools let the agent
create recurring (`cron_expr`) or one-time (`run_in_minutes`) schedules
directly from a chat message, with an optional per-schedule `allowed_tools`
allow-list and guardrails against accidental high-frequency schedules
(`min_schedule_interval_minutes`) and per-user sprawl
(`max_schedules_per_user`). Schedule creation is rejected up front for
identities that can't be reliably resolved later (`IdentityMiddleware`'s
synthetic fallback ID), rather than silently failing at fire time.
`pincer schedule add`/`remove` CLI commands no longer exist — creation,
removal, and toggling happen entirely through chat.

**`Agent.run_headless`**: a session-free execution path so scheduled prompts
actually run through the LLM with tool access, instead of echoing a stub
string.

**Standalone worker for horizontal scaling**: `pincer run tasks` starts only
the background task worker (no channels, no API/MCP export, no live
email/calendar polling) — requires `PINCER_TASK_BROKER=redis` since the
in-memory broker can't be shared across processes. `docker-compose.yml`'s
`http` profile now ships a `redis` service and a `pincer-http-tasks` worker
service alongside the main `pincer-http` service as the reference topology.

**Fixes bundled in this rework:**
- repid's own worker no longer swallows `SIGINT`/`SIGTERM` during pincer
  shutdown (`register_signals=[]` — pincer's shutdown sequence owns signal
  handling end-to-end)
- Scheduled digest delivery failures are no longer logged as successful
- `PINCER_IDENTITY_MAP` now supports single-channel entries (previously
  required at least two linked channel:id pairs)
- repid's expected CRITICAL cancellation traceback is silenced during
  normal shutdown

See [Background Tasks](../core-components/background-tasks.md) for the full
architecture and config reference.
