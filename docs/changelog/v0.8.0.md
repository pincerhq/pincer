# Pincer 0.8.0 — Skills Deprecated, MCP as the Extension Standard

**Status:** Upcoming release
**Install preview:** `pip install -U pincer-agent`

---

## TL;DR

0.8.0 formally deprecates the Skills system. Skills continue to load and run
unchanged through all 0.8.x releases. They are removed entirely in 0.9.0.

MCP servers are now the recommended way to extend Pincer.

---

## Why Skills are being retired

The Skills system (`skills/` directory, `@tool` decorator, `pincer skills` CLI)
was Pincer's original extensibility model. It served well early on, but MCP has
proven to be a better foundation for the same goals:

| Property | Skills | MCP servers |
|----------|--------|-------------|
| Language | Python only | Any (Python, Node.js, Go, Rust, …) |
| Isolation | Interpreter-level (limited) | Subprocess sandbox (`MCPSandbox`) |
| Interoperability | Pincer only | Claude Desktop, Cursor, VS Code, any MCP client |
| Distribution | GitHub + `pincer skills install` | `pip`, `npm`, `cargo`, Docker Hub |
| Security scanning | Pincer-specific AST scanner | MCP sandbox blocks env leakage by default |
| Spec compliance | None | MCP 1.x — open standard |

Skills required Pincer to own the entire lifecycle — distribution, security
scanning, sandboxing, signing. MCP delegates all of that to the standard and
to OS process isolation, which is more robust and independently verifiable.

## Timeline

| Version | Date | Change |
|---------|------|--------|
| **0.8.0** | Upcoming | Skills deprecated. Deprecation notice shown at startup when `skills/` directory is non-empty. `pincer skills` commands emit deprecation warnings. **MCP servers configured in `pincer.toml` disable skills entirely** — skill loading is skipped when any `[[mcp.servers]]` entry is present and MCP is enabled. |
| **0.8.x** | Ongoing | Skills continue to load and run when no MCP servers are configured. Skills and MCP are mutually exclusive. |
| **0.9.0** | Future | Skills removed. `skills/` directory ignored at startup. `pincer skills` subcommands removed. Skill loader, sandbox, scanner, and signing modules deleted. |

## Migration guide

### Step 1 — Create an MCP server

For each skill, create a FastMCP server. The tool logic stays the same; only
the registration mechanism changes.

**Before** (`skills/weather/main.py`):

```python
from pincer.tools import tool
import httpx

@tool(name="get_weather", description="Get current weather for a city")
async def get_weather(city: str) -> str:
    async with httpx.AsyncClient() as client:
        resp = await client.get(f"https://wttr.in/{city}", params={"format": "j1"})
        data = resp.json()
        current = data["current_condition"][0]
        return f"Weather in {city}: {current['temp_C']}°C, {current['weatherDesc'][0]['value']}"
```

**After** (`mcp-servers/weather/server.py`):

```python
from fastmcp import FastMCP
import httpx

mcp = FastMCP(name="weather", instructions="Provides current weather data.")

@mcp.tool
async def get_weather(city: str) -> str:
    """Get current weather for a city."""
    async with httpx.AsyncClient() as client:
        resp = await client.get(f"https://wttr.in/{city}", params={"format": "j1"})
        data = resp.json()
        current = data["current_condition"][0]
        return f"Weather in {city}: {current['temp_C']}°C, {current['weatherDesc'][0]['value']}"

if __name__ == "__main__":
    mcp.run(transport="stdio")
```

### Step 2 — Register the server in `pincer.toml`

```toml
[[mcp.servers]]
name      = "weather"
transport = "stdio"
command   = "python"
args      = ["mcp-servers/weather/server.py"]
sandbox   = true
approval_required = ["none"]   # weather is read-only
```

### Step 3 — Remove the skill directory

```bash
rm -r skills/weather
```

Pincer auto-discovers the MCP server on next `pincer run`. The tool appears
in the agent loop as `weather__get_weather` (with `tool_prefix = true`, the
default).

## Running MCP servers in HTTP mode

MCP servers can also run as persistent HTTP services instead of per-request
subprocesses. This is useful for servers that need to maintain state (database
connections, caches, long-lived sessions) or for sharing a server instance
across multiple Pincer deployments.

See [MCP Servers](../core-components/mcp-servers.md) for a full
comparison and configuration reference.

## Bundled MCP servers

Pincer 0.8.0 ships three ready-to-use MCP servers in the `src/` workspace:

| Server | Package | What it does |
|--------|---------|--------------|
| `pomodoro-mcp` | `pomodoro-mcp` | Pomodoro timer — sessions, stats, history |
| `pincer-mcps` | `pincer-mcps` | Translation, summarization, stock prices, weather, news |
| `sqlite-vec-memory-mcp` | `sqlite-vec-memory-mcp` | Semantic memory via sqlite-vec + ONNX embeddings |

Install and configure any of them with a single `[[mcp.servers]]` entry.
They support both stdio (default) and HTTP transport out of the box.

## Frequently asked questions

**Do I have to migrate before 0.9.0?**

No. Skills load and run unchanged through all 0.8.x releases. You have time to
migrate at your own pace. 0.9.0 will be announced at least one minor version
in advance.

**Will `pincer.tools.tool` be removed?**

The `@tool` decorator itself is not removed — it is used internally and may be
useful for MCP server authors who want typed tool wrappers. What is removed is
the *skill loader* that scans `skills/` directories and auto-registers tools
found there.

**Can I keep running a skill without migrating?**

Yes, through 0.8.x. After 0.9.0, you can still run the skill's code as an MCP
server — just wrap the `@tool` functions in a FastMCP app instead of
registering them via the skill loader.

## Memory backend unification

The memory subsystem has been refactored around a single abstract interface
(`BaseMemoryBackend`) that both the built-in SQLite backend and the
`sqlite-vec-memory-mcp` backend now implement identically.

### Unified method set

Every backend now exposes the same methods:

| Method | Description |
|---|---|
| `store_memory(user_id, content, category, embedding, extra_tags)` | Persist a record; returns its ID |
| `get_memory(memory_id)` | Fetch one record by ID; `None` if not found |
| `list_memories(user_id, limit, offset, category, tags, match_all_tags)` | Paginated listing with filters |
| `update_memory(memory_id, content, category, tags)` | In-place field update |
| `delete_memory(memory_id)` | Delete one record |
| `delete_user_memories(user_id)` | Delete all records for a user; returns deleted count |
| `count(user_id)` | Total record count, optionally scoped to a user |
| `search_text(query, user_id, limit, tags)` | Full-text / keyword search |
| `search_similar(embedding, user_id, limit, tags)` | Vector similarity search |

The MCP backend now implements `get_memory` via a new `memory_get` tool on the
`sqlite-vec-memory-mcp` server.

### Tag search modes

`list_memories` accepts a `match_all_tags` boolean (default `False`):

| Mode | Behaviour | SQL equivalent |
|---|---|---|
| `match_all_tags=False` (default) | Records matching **any** provided tag (OR logic) | `WHERE tag IN (...)` |
| `match_all_tags=True` | Records matching **all** provided tags (AND logic) | `GROUP BY id HAVING COUNT(DISTINCT tag) = N` |

This is important for the conversations API, which uses `match_all_tags=True` to
AND-combine the `user_id`, `category:exchange`, and optional channel tag filters
so that a wrong channel identifier returns no results.

### Tag naming conventions

Tags follow a colon-separated namespace scheme:

| Tag | Meaning |
|---|---|
| `user:{user_id}` | Record belongs to this user |
| `category:{category}` | Record category (e.g. `exchange`, `general`, `profile`) |
| `user:{channel}:{channel_user_id}` | Record originated from a specific channel user |

### `sqlite-vec-memory-mcp` improvements

The bundled semantic memory server gained two new capabilities in its
`memory_list` tool:

- **`offset`** — skip the first N records for cursor-style pagination
- **`match_all`** — when `true`, returns only records that carry *all* provided
  tags (AND logic); default `false` preserves the previous OR behaviour

A new **`memory_get`** tool was added to fetch a single record by integer ID.

## Conversations API rework

`GET /api/conversations` is now backed by the active memory backend rather than
the raw `conversations` SQL table. Key changes:

- **`user_id` is now required** — all queries are scoped to a specific user
- **Channel filtering** uses the compound tag `user:{channel}:{channel_user_id}`;
  both `channel` and `channel_user_id` must be provided together
- **`offset` pagination** replaces cursor-based navigation
- **Messages are pre-split** in the response — each conversation item includes a
  `messages` array with separate `user` and `assistant` objects rather than a
  raw content blob
- **`category:exchange` is always enforced** — only agent exchanges are surfaced,
  not internal summaries or profile records

See [REST API reference](../reference/rest-api.md#conversations) for the full
request/response shape.
